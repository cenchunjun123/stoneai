# ISaGRAF 5.x POU 加密源码解密规范

来源：基于真实工程 `27750.000.001.04 HeatPipeCoolerInDoorController`
（ISaGRAF 5.50.7 + c.suite 5.1.9，73 个 POU）完整破解验证通过，
375.9 KB / 约 1.5 万行 ST 源码全部恢复，中文注释完好。

## 一句话原则

**这是 XOR 流密码，不是 AES/RC4。密钥流只与字节绝对位置有关、与内容无关，
前 21 字节是固定文件头。用「关键字 + POU 名字」做已知明文攻击即可完整破解。**

---

## 一、加密格式识别（30 秒判定）

### 1.1 载体形态

| 载体 | 说明 |
|---|---|
| `*.pp1` | **工程导出包**（ZIP），内含 `Manifest.xml` + 每个 POU 一个 `.isaxml` + `*Variables.xml` |
| 工程目录 `.otsln` | `PrjLibrary.mdb`（Jet4 Access）+ `Programs/<name>/<name>.isaxml` |

### 1.2 判定特征

打开任意 `.isaxml`，找 `<PouBody><![CDATA[...]]></PouBody>`：

```
密文 = Base64Decode( CDATA 内容 )
密文[0:21]  = 80 54 27 57 53 5b 5a 2f 5d 64 65 13 64 6a 1f 69 6c 31 33 35 37  （固定头）
密文[21:]   = 明文 XOR K
```

**铁律：密文长度 ≈ 文本长度（Base64 解码后），没有膨胀**——
这立刻排除 AES/RC4（分组密码会填充）和压缩格式。

### 1.3 差分速测（确认 XOR）

找两个**代码几乎相同**的 POU（如 `Cov1ValveControl` / `Cov2ValveControl`、
`Limit_DINT` / `Limit_UINT`）：

```
Δcipher[i] = cipher_A[i] XOR cipher_B[i]
```

若 Δ 只出现在少数位置且 **XOR 差值 = 明文字符差**（如 `'1'^'2'=0x03`、
`'D'^'U'=0x11`），则**确证 XOR 流密码且密钥流相同**。

> **关键**：用 XOR 而非减法。加法差值不一致（+3/+1/+1/+1）会误导成仿射密码，
> XOR 差值完全一致（全 0x03 / 全 0x11）才指向流密码。**这是本次破解走过的主要弯路。**

## 二、密钥流 K（已验证常量）

### 2.1 两种变体

PouBody 有**两种加密变体**，由头部第 0 字节标识：

| 变体 | 头字节 | 密钥流 | 适用 |
|---|---|---|---|
| **A** | `0x80` | 偏移 21..28 引导段 `C5 06 05 04 03 02 01 00`，偏移 29 起周期 8 循环 `41 C4 05 04 03 02 01 00` | 绝大多数 POU |
| **B** | `0xC0` | 偏移 21 起周期 13 循环 `37 28 19 0A 3C 2D 1E 0F 00 32 23 14 05`（无引导段） | 巨型 POU（实测为 32 机组群控块） |

两种变体前 21 字节均为固定头，其中字节 17-20 恒为 `31 33 35 37`（"1357"）。

### 2. 生成规则

```
变体 A:  K[i<21]=0;  K[21..28] = 引导段;  K[i>=29] = LOOP[(i-29) % 8]
变体 B:  K[i<21]=0;  K[i>=21] = LOOP_B[(i-21) % 13]
```

特征：**块内倒计数**。变体 A 记住 `... 05 04 03 02 01 00` 尾巴，
变体 B 记住 `... 1E 0F 00` + `32 23 14 05` 两段倒计数。在新工程里先搜这些标志。

### 2.3 变体识别的坑

**头字节识别不完全可靠**：实测 73 个 POU 里 11 个头字节是 `0xC0`，但只有 2 个
真正用变体 B 密钥流，其余 9 个仍用变体 A。**必须用「解密后是否合法」做二次校正**：
先按头字节赋变体，解不对的 POU 切换到另一种变体重试。工具已自动完成这步。

## 三、破解步骤（工具已自动化，供理解与排错）

### 3.1 已知明文攻击

所有 **ST 语言 POU**（`Manifest.xml` 的 `Language="ST"`）以如下开头：

```
FUNCTION_BLOCK <POU名>     Kind="FunctionBlock"
FUNCTION <POU名>           Kind="Function"
PROGRAM <POU名>            Kind="Program"
```

POU 名字从 `Manifest.xml` 的 `<Pou Name="..." Kind="..." Language="..."/>` 读取。
于是偏移 21 起的明文完全已知，`K[i] = cipher[i] XOR plain[i]`。

### 3.2 交叉一致性验证

对**所有** POU 求 K，按偏移统计：正确时**绝大多数 POU 给出同一个 K 值**。
出现 `主值×N / 异值×2` 的分裂是正常的——异类来自头几个字节不同（如 FBD 残留），
取众数即可。`Alarm_Mng.st` 等 65/73 一致就是确证。

### 3.3 相位确定

触发条件（任一即可）：
- `Limit` 类 POU 解出 `:=`
- 任意 POU 解出 UTF-8 中文（`E6 8A A5` = 「报」）
- 任意 POU 解出 `\x0a\x0d` 换行或 `(*` 注释

### 3.4 全量验证

解密后检查：`plain[21:21+len(kw)] == kw` 命中率应 **≥ 95%**。
未命中的少数是变体识别错误或 FBD 语言 POU，属正常。

> **坑**：`Manifest.xml` 里 `Language="FBD"` 的 POU（通常 6 个左右）**不以**
> `FUNCTION_BLOCK` 开头，别用它们求 K，也别把它们当解密失败。
> FBD POU 解密后是文本化的图形表示：`PROGRAM Xxx\n#info= FBD\n@@NBID=...`。

### 3.5 变体校正（关键收尾）

头字节 `0x80`/`0xC0` 只是**初判**。按 3.4 验证时，凡解不出的 POU 就切换
到另一种变体重试。实测 11 个 `0xC0` 头里 9 个其实用变体 A——只有
`Unit_Network_32` / `UnitsRotation_32`（32 机组群控）真正用变体 B。
校正后应达到 **73/73 = 100%**。

## 四、自动化工具

`decrypt_isagraf.py`（与本 SKILL.md 同目录）：

```bash
# 解密 .pp1 包
python decrypt_isagraf.py -p 工程.pp1 -o 输出目录

# 解密工程目录下的所有 .isaxml
python decrypt_isagraf.py -d "C:\...\ Programs" -o 输出目录

# 内置密钥失效时：自动重推（--recover）再用关键字已知明文攻击
python decrypt_isagraf.py -p 工程.pp1 -o 输出 --recover
```

输出：每个 POU 一个 `.st` 文件 + `_解密报告.md`（含每个 POU 的命中状态）。

工具内置三级策略，自动降级：
1. **内置常量**直接解（秒级）
2. 验证失败 → `--recover` 时从 `Manifest.xml` 自动重推 K
3. 推不出 → 提示用差分速测找相似 POU 对

**前置条件**：`.pp1` 是标准 ZIP；`.isaxml` 是 UTF-8 XML。无需 STone/ISaGRAF 环境，
纯 Python 标准库，任何机器能跑。

## 五、避坑清单（全部实测）

1. **不要猜 AES/RC4/压缩**。长度不膨胀 + 差分一致 = XOR 流密码。先做差分速测。
2. **差分用 XOR 不用减法**。加法差会不一致，误判成仿射密码浪费大量时间。
3. **前 21 字节是头部**。它们在所有 POU 中完全相同（17-20 恒为 "1357"），不参与加密。
4. **密钥流与内容无关**。不同 POU、不同长度，同一位置用同一 K 字节（同一变体内）。
5. **存在两种变体**。`0x80` 头 = 引导段+周期 8；`0xC0` 头 = 周期 13。
   **头字节只是初判**，必须用「解密合法性」二次校正。
6. **FBD 语言 POU 不以关键字开头**。求 K 时排除 `Language="FBD"`，验证时它们以
   `#info= FBD` 标识，属正常解密成功。
7. **明文含 UTF-8 中文**。`Alarm_Mng` 等注释是中文，解密评分要给 `>=0x80` 字节部分分，
   否则会误判可读率。
8. **`.pp1` 是 ZIP**（PK 头）。用 `zipfile` 直接解压，别被 `.pp1` 扩展名骗了。
9. **`Manifest.xml` 是地图**。POU 名字 / 类型 / 语言全在里面，是已知明文攻击的本钱。
10. **变体 A 引导段与循环段不同**。`K[21..28] = C5 06 ...` 而 `K[29+] = 41 C4 ...`，
    别把引导段误认为周期的一部分。
11. **变体 B 的周期 13 容易被误判**。用名字推导时短前缀会造成「周期 13/16 都成立」的
    假象，必须用**尾部** `END_FUNCTION_BLOCK`（18 字节、位于不同长度处）交叉验证真实周期。

## 六、迁移到 STone 的衔接

解密出的 `.st` 迁移 STone 时需转换的语法（详见 `my-stoneai-skill`）：

| ISaGRAF | STone |
|---|---|
| `SecToTime(n)` | `INT_TO_TIME` 或 `T#ns` 字面量 |
| `AlarmOnDely(IN, PT)` | TON 实例化调用 |
| `ANY_TO_DINT` | 需验证，否则 `DINT(...)` |
| `g_xxx` 全局变量 | STone 全局变量表重建 |
| 旧库 `IPCfg`/`CAREL_BASIC_LIB` 等 | `add_library` 按需添加 |
